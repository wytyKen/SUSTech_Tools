## 2026-09 修复：适配 TIS 升级
**现象**：2026 年秋起，原版脚本 CAS 显示"登录成功"后立即崩溃（`IndexError`，即原仓库 issue #36 的"登录后闪退"）。  
**原因**：TIS 完成平台升级（Spring Session 化），CAS 回跳后不再下发 `route`/`JSESSIONID`，改为 `SESSION` cookie；同时对查询类接口加严了用户级频控（返回 `"查询请求频率过高"`）。

**本 Fork 的修改**：
1. **SESSION cookie 适配**：`cas_login` 改用 `requests.Session` 跟随 CAS 回跳后的全部重定向并提取 `SESSION`；若票据被拒被踢回 CAS，会明确提示而不是崩溃
2. **查询限流自动退避重试**：`queryKxrw` 每个选课类别被限流后按 5→15 秒逐步退避重试（最多 15 次），类别之间固定间隔 2 秒；`queryXkdqXnxq` 同样处理。**全量拉取约需 1~2 分钟，期间出现"被限流，N秒后重试"属正常**
3. **抢课请求遇限流**：额外等待 3 秒，且不会把限流回执误判为"已满/冲突"而跳课
4. **修复并发竞态**：叠加抢同一门课时，后到的重复请求会返回"已选"，原版会因此误删队列中的**下一门课**并提前退出。现自动跳课仅认"冲突/已满"；若课程实际"已选"，输入任意字符回车手动跳过即可
5. 每个类别打印实际返回门数，便于核对是否拉全（2026-09-07 实测全量 745 门）

**建议的抢课流程**：
- 选课开放前先跑一次脚本，把全量课程缓存进 `course.txt`（提示保存时选 y）；某类别没拉全时，删除 `course.txt` 重跑即可补齐
- 抢课当天**提前 10 分钟左右启动**：直接读缓存、不发查询请求，避开整点 CAS 拥堵与查询限流；登录后确认目标课程在列，进入模式 1 待命
- 待命期间每隔几分钟按一次回车保活（返回"不在设置的时间范围内"属正常、无害）
- 到点后按回车开抢，**一组 3 连发约 4 秒，跑完看清回执再按下一组**；连点叠加收益极低且更易触发限流

**常见回执速查**：
| 回执 | 含义 | 处理 |
|---|---|---|
| 蓝色框"成功" | 已选上 | 无 |
| 不在设置的时间范围内 | 选课尚未开放 | 继续等待 |
| 查询请求频率过高 | 被限流 | 程序自动退避重试，无需干预 |
| 陌生文案且一直不跳课 | 服务端提示语有变 | 输入任意字符回车手动跳过 |
| 大量 JSON/报错刷屏 | 会话过期 | 重启脚本重新登录（缓存仍在） |

## 使用说明  
- main.py为Python3编写的主程序，运行即可  
- class.txt为需要选择的课程列表，一行一个数据，因编码问题，第一行请留空或不要编辑。  
**选课顺序会严格按照class.txt中录入的先后顺序进行，在高优先级课程被选完/冲突前不会选低优先级课程，除非手动输入任意值字符回车跳过**  
- 按下回车之后会进入一个3s的循环，每秒选当前最优先的课程一次。（可以按多次开启多个计时循环）
